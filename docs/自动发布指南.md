# 自动发布指南

本仓库通过 `.github/workflows/release.yml` 将构件发布到 GitHub Releases、Modrinth 和 CurseForge。
完整发布流程由 `main` 上的 `v*` 标签触发，但只构建远程 `mc/*` 分支，不构建 `main`。已有模组版本需要新增 Minecraft 支持时，也可以手动补发单个 `mc/*` 分支。

## 1. 发布平台配置

项目标识：

| 平台       | 项目 ID    | 项目地址                                                      |
| ---------- | ---------- | ------------------------------------------------------------- |
| Modrinth   | `zak1wIOR` | `auto-torch-skr`                                              |
| CurseForge | `1617474`  | <https://www.curseforge.com/minecraft/mc-mods/auto-torch-skr> |

在 GitHub 仓库的 `Settings > Secrets and variables > Actions` 中配置以下内容。

Repository secrets：

| 名称               | 内容                  |
| ------------------ | --------------------- |
| `MODRINTH_TOKEN`   | Modrinth 个人访问令牌 |
| `CURSEFORGE_TOKEN` | CurseForge API Token  |

Repository variables：

| 名称                    | 内容       |
| ----------------------- | ---------- |
| `MODRINTH_PROJECT_ID`   | `zak1wIOR` |
| `CURSEFORGE_PROJECT_ID` | `1617474`  |

不需要配置 GitHub Token。工作流使用 GitHub 自动提供的 `GITHUB_TOKEN`。
不得将 Token 写入仓库、`gradle.properties`、文档或工作流文件。

Modrinth Token 的最小权限：

- 项目：读取项目。
- 版本：创建版本。

如果以后需要自动修改已经发布的 Modrinth 版本，再增加读取版本和写入版本权限。不需要项目删除、版本删除、用户资料、组织、通知或提款权限。

## 2. 分支规则

每个需要发布的 Minecraft 版本对应一个远程分支：

```text
mc/<Minecraft 版本>
```

例如：

```text
mc/1.20.6
mc/1.21.1
mc/1.21.11
mc/26.1.2
mc/26.2
```

工作流会动态查找所有 `origin/mc/*` 分支。无需在工作流中手动维护版本列表，也无需把 `release.yml` 同步到这些分支。

分支必须满足以下条件：

- 分支名中的 Minecraft 版本与 `gradle.properties` 的 `minecraft_version` 一致。
- `gradle.properties` 的 `mod_version` 与发布标签一致。
- 分支修改已经提交并推送到远程仓库。
- Fabric、Forge 和 NeoForge 均能完成构建。

例如发布标签为 `v1.4.3` 时，所有准备发布的 `mc/*` 分支都必须包含：

```properties
mod_version=1.4.3
```

只存在于本机工作区、尚未推送的提交不会进入 GitHub Actions。

## 3. 发布前验证

在每个 `mc/*` 分支完成对应版本的修改，然后使用 Java 25 验证：

```powershell
$env:JAVA_HOME='C:\Software\Deps\Java\jdk-25.0.3'
$env:Path="$env:JAVA_HOME\bin;$env:Path"
.\gradlew.bat clean build --no-parallel --max-workers=1 --console=plain
git diff --check
```

完成必要的游戏内冒烟测试后，提交并推送该分支：

```powershell
git add .
git commit -m "发布: v1.4.3"
git push origin mc/<Minecraft 版本>
```

对所有准备发布的 `mc/*` 分支重复以上步骤。

> 记得在 github 上等 build 任务都完成了再发布带 tag 的 release 任务，防止出现构建失败，导致发布顺序有问题的情况。

## 4. 更新日志

默认情况下，工作流会收集上一个版本标签到当前标签之间的提交，并根据 `.githooks/commit-msg` 规范化后的提交类型生成中文更新日志。

生成的日志会：

- 显示模组版本。
- 根据全部远程 `mc/*` 分支计算 Minecraft 最低版本和最高版本。
- 按照提交类型分类，并省略没有内容的章节。
- 忽略 `发布: v<版本>` 这类纯版本发布提交。
- 将不符合已知类型的历史提交放入“其他”章节。
- 附加上一个版本到当前版本的 GitHub 完整变更链接。

支持的提交类型与 `.githooks/commit-msg` 保持一致

例如，以下提交：

```text
新增: 添加自动补充火把功能
优化: 降低大型选区的查询开销
修复: 修复Y轴世界边界处理
发布: v1.4.3
```

会自动生成类似下列内容：

```markdown
## Auto Torch v1.4.3

适用于 **Minecraft 1.20.6~26.2 / NeoForge、Forge、Fabric**。

### 新增

- 添加自动补充火把功能

### 修复

- 修复Y轴世界边界处理

### 优化

- 降低大型选区的查询开销

**完整变更**：https://github.com/sakurakugu/auto-torch/compare/v1.4.2...v1.4.3
```

自动更新日志只会读取当前发布标签可达的提交，也就是 `main` 上两个版本标签之间的提交。仅存在于 `mc/*` 分支、没有合并或拣选到 `main` 的提交不会出现在更新日志中。

特殊版本仍可以在 `main` 根目录创建非空的 `RELEASE_NOTES.md`。工作流会优先原样使用该文件，不再自动生成内容。手工编写时必须在每次发布前更新或删除该文件，避免重复发布上一个版本的内容。

无论内容是自动生成还是由 `RELEASE_NOTES.md` 提供，同一份更新日志都会发布到 GitHub、Modrinth 和 CurseForge。

## 5. 创建发布标签

确认所有 `mc/*` 分支均已提交并推送后，回到 `main`。`main` 必须已经包含发布工作流和需要写入自动更新日志的提交；如果采用手工更新日志，还必须包含本次的 `RELEASE_NOTES.md`。

```powershell
git switch main
git pull --ff-only
git add .
git commit -m "发布: v1.4.3"
git push origin main
git tag v1.4.3
git push origin v1.4.3
```

不使用手工更新日志时，无需创建 `RELEASE_NOTES.md`。标签必须指向已经推送到 `main` 的发布提交。

不要移动或覆盖已经发布的标签。发现问题时应修复后发布新的补丁版本。

## 6. 工作流行为

标签推送后，工作流依次执行：

1. 校验两个平台的仓库机密和仓库变量。
2. 查找全部远程 `mc/*` 分支并锁定各分支当前提交 SHA。
3. 校验分支名、`minecraft_version`、`mod_version` 和标签。
4. 分别构建并测试每个 Minecraft 版本的 Fabric、Forge 和 NeoForge 构件。
5. 所有版本构建成功后生成更新日志，并创建一个 GitHub Release。
6. 将每个 Minecraft 版本的三个加载器构件分别发布到 Modrinth 和 CurseForge。
7. 将全部 JAR 上传到同一个 GitHub Release。

平台版本号包含模组版本、Minecraft 版本和加载器，例如：

```text
1.4.3+mc1.21.1.fabric
1.4.3+mc1.21.1.forge
1.4.3+mc1.21.1.neoforge
```

这样不同 Minecraft 版本和加载器不会使用重复的平台版本号。

如果任一 `mc/*` 分支构建失败，GitHub Release 和平台发布阶段都不会开始。发布阶段的单个目标失败时，其他目标仍会继续执行，失败项需要在 GitHub Actions 日志中检查。

## 7. 向已有版本补发 Minecraft 版本

已有 GitHub Release 需要增加一个 Minecraft 版本时，保持 `mod_version` 不变，并完成该版本的迁移、构建、游戏内验证、提交和推送。例如给 `v1.4.3` 补充 Minecraft 26.3：

```properties
minecraft_version=26.3
mod_version=1.4.3
```

将提交推送到 `mc/26.3` 后：

1. 打开 GitHub 仓库的 `Actions > Release`。
2. 选择 `Run workflow`。
3. `release_tag` 输入已有标签 `v1.4.3`。
4. `minecraft_version` 输入 `26.3`。
5. 运行工作流并检查构建和三个平台的发布结果。

手动补发会校验标签、已有 GitHub Release、远程分支名、`minecraft_version` 和 `mod_version`。它只构建并发布指定的 Minecraft 版本，不会重新发布其他 `mc/*` 分支；GitHub Release 的标题和发行说明会更新为当前远程分支覆盖的版本范围。不得通过移动已有标签来补发版本。

## 8. 查看发布结果

- GitHub：仓库的 `Releases` 页面包含更新日志和全部 JAR。
- Modrinth：项目版本页面包含加载器、Minecraft 版本、下载量和文件信息。
- CurseForge：项目 Files 页面包含审核状态、游戏版本、加载器和下载量。
- GitHub Actions：仓库的 `Actions > Release` 页面包含每个 Minecraft 版本的构建和发布日志。

Modrinth 项目处于 `processing` 或审核状态时，公共 API 和项目页面可能暂时不可见，但具有正确权限的项目 Token 仍可读取项目。
